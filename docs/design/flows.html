Background risk check

Why it runs in the background

Real KYB providers are slow (seconds to minutes) and sometimes fail. If the API waited for them, a request could hang or time out. Instead, submitting puts a job on a BullMQ queue (stored in Redis) and the API answers 202 Accepted immediately. A separate worker picks up the job. We simulate the provider, including random delays and failures.

Retries with backoff

If the provider call fails, the worker throws an error and BullMQ tries again later, waiting longer each time (exponential backoff, for example 2 s → 4 s → 8 s → 16 s). The number of attempts and the delays are set in configuration. When every attempt has failed, the risk status becomes FAILED, the application stays SUBMITTED, and an ADMIN can trigger a retry.

Idempotency: running twice has the same effect as running once

Duplicates happen in real systems: a double-clicked submit, or a worker that crashes after saving but before marking the job done. Three layers protect us:

  1. Queue level: the job ID is built from the application and submission number, e.g. risk:101:1. BullMQ ignores a new job whose ID already exists.
  2. Worker level: before calling the provider, the worker checks whether a completed result already exists for that application and submission. If it does, it does nothing.
  3. Database level: UNIQUE (application_id, submission_number) on risk_assessments. Even two workers running at the same moment can't store two results.

Implementation notes

A manual ADMIN retry must use a new job ID (e.g. risk:101:1:r1). BullMQ silently ignores a job whose ID is still stored, even a failed one.

The worker never logs decrypted national IDs or the provider's raw request.

Concurrency: row locks

Every state-changing action runs inside a database transaction that first locks the application row (SELECT … FOR UPDATE). A second request on the same application waits until the first one commits, then checks the new state.

The worker takes the same lock when it saves a risk result, so a reviewer action and a worker update can't clash either. The lock only covers one application row, so different applications never wait for each other.
