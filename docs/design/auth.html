Authentication & sessions

Access and refresh tokens, rotation with reuse detection, and the login rules.

Login returns a short-lived access token and a longer-lived refresh token:

POST /api/v1/auth/login   → 200
{
  "accessToken": "eyJ…",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "refreshToken": "8Kp3…",
  "refreshExpiresIn": 604800,
  "user": { "id": "…", "fullName": "Sita", "role": "SALES" }
}
Access tokenRefresh token
FormatJWT signed with a server-side secret; claims: user ID and role32 random bytes, base64url-encoded
Lifetime15 minutes (configurable)7 days (configurable)
Stored on the serverNoOnly its SHA-256 hash, in refresh_tokens
How it's checkedSignature and expiry, then one lookup confirming the user still exists and is activeDatabase lookup by hash
RevocableNo; it simply expiresYes: one token, or its whole family

The user lookup on every request means a deactivated user is locked out immediately, and the role used for permission checks always comes from the database, not from the token.

Refresh token rotation with reuse detection

Rules

  • Logout revokes the refresh token's whole family and returns 204.
  • Login failures all look the same. Unknown email, wrong password and deactivated account all return 401 "Invalid email or password", so nobody can discover which emails exist.
  • Rate limiting: login and refresh allow a few attempts per minute per IP (for example 5), then return 429.
  • Simultaneous refreshes with the same token: the token row is locked, so the second request sees it already used and is treated as reuse. That's strict, but safe.
  • Tokens travel in the JSON body, not cookies. This is an API-only service, and it keeps Swagger testing easy. A browser frontend would use httpOnly cookies instead.
  • Audit: LOGIN_SUCCEEDED, LOGIN_FAILED, LOGOUT and REFRESH_TOKEN_REUSE_DETECTED are recorded. Normal refreshes aren't, to avoid noise.

Trade-off: after logout, the access token keeps working until it expires, at most 15 minutes. That's the price of not checking a blocklist on every request.
